# Research on Big-Data-Laboratory Troubleshooting Question-Answering System Based on RAG and Multi-Agent Collaboration

Reproducibility package for the final paper *"基于 RAG 与多智能体协同的大数据实验室故障排查问答系统研究"*
— English title: *Research on Big-Data-Laboratory Troubleshooting Question-Answering System
Based on RAG and Multi-Agent Collaboration* (Yajie Gao, Wenzhou-Kean University, course 5801).
This exact string is used as the H1, the bibtex `title`, the repository description and the
manuscript title; the earlier working subtitle "Verifying Version-Compatibility Claims" is
dropped.

The system answers troubleshooting questions about a Hadoop / Spark / Hive / HBase teaching
cluster. Its distinguishing problem is **version compatibility**: the same error text has a
different root cause under Spark 3.4 and Spark 3.5, so a fluent answer that quotes a version
number not present in the retrieved evidence is wrong even when the prose looks right.
The system therefore runs a serial chain of agents that is allowed to *decline*:

```
question + evidence  ->  Proposer  ->  Reviser  ->  Checker  ->  answer
                         (draft)      (version      (claim-by-claim,
                                       check)        removes unsupported claims)
```

This repository contains the complete code, the dataset, the configuration files and the
frozen result files that produced every number, table and figure in the paper.

---

## 1. Research objective

1. Quantify how much of the improvement in a troubleshooting QA system comes from
   **retrieval** and how much from **multi-agent verification**.
2. Test whether a *deterministic* rule-based version filter can replace an LLM verifier,
   i.e. whether the multi-agent design is necessary at all.
3. Measure the cost of verification in answer coverage, latency and tokens.

## 3. Hardware requirements

* **No GPU is required to run anything in this repository.** There is no training step:
  the three agents are prompt-only calls to a hosted chat model, and the deterministic
  filter baseline is pure Python.
* The reported experiments ran on a **MacBook Air (Apple silicon, 16 GB RAM, macOS)**,
  CPU only, against a remote OpenAI-compatible endpoint.
* The course-provided **NVIDIA RTX A5000** was *not* used, because neither inference nor
  evaluation needs a GPU here (all model calls are remote). The repository is nevertheless
  designed to run on the A5000 machine unchanged: `pipeline.py` only needs `OPENAI_API_KEY`
  and `OPENAI_BASE_URL`, and every script is CPU-bound. If you want to serve the model
  locally instead of calling an API, point `OPENAI_BASE_URL` at a local vLLM / Ollama
  server exposing an OpenAI-compatible `/v1` route — the A5000 (24 GB) fits a 7B-class
  model at 4-bit, and nothing else in the code has to change.
* Wall-clock for the full main experiment (700 model calls, 100 cases × 4 configurations):
  about 2.5 hours on the MacBook Air, dominated by remote API latency (mean 6.6 s per
  single-turn call, 48.9 s per full-pipeline case). Re-running evaluation only takes
  seconds and needs no API at all.

Recorded settings (all in `configs/proposed_model.yaml`):

| item | value |
|---|---|
| generation model | `glm-5.3-flash` (Zhipu BigModel, OpenAI-compatible endpoint) |
| endpoint | `https://open.bigmodel.cn/api/paas/v4` |
| temperature / top-p | 0.1 / 0.8 |
| max new tokens | 3072 (the provider forces a "thinking" phase; 3072 is the smallest budget that reliably returns non-empty `content`; empty answers are retried at 8192) |
| seeds | split seed 42 (frozen, shipped in the CSV); prompts and decoding contain no random sampling |
| decoding | deterministic-ish (temperature 0.1); the provider exposes no seed parameter |

| similarity threshold | Chroma `similarity_threshold=0.7` — **design value only, never applied** (oracle evidence is used, see §6) |
| pricing | API credits were donated → cost logged as USD 0 |

No machine-specific paths are hard-coded: the four experiment drivers (`run_real_experiment`,
`run_bare_baseline`, `run_injection`, `filter_baseline`) read `configs/*.yaml` through
`src/config.py`, and data/results paths are relative to the repository root.

## 6. Dataset

| item | value |
|---|---|
| name | `bigdata_error_cases_500_en` |
| location | `data/bigdata_error_cases_500_en.csv` (296 KB, committed) |
| size | 500 cases, 4 components × 125 (Hadoop, Spark, Hive, HBase) |
| fields | `id, component, question, context, ground_truth, source, split, status` |
| evidence | `context` — the documentation span that governs the case (≈190 characters) |
| gold | `ground_truth` — a 3–5 step repair procedure |
| sources | Apache official docs, Apache JIRA tickets, Stack Overflow threads, and the course laboratory's own fault log; each row carries its `source` URL |
| split | frozen: `kb` = 400, `test` = 100, stratified 8:2 per component, seed 42 |
| leakage | verified zero: no test question and no test evidence span appears in `kb` |

`data/README.md` documents provenance and schema in detail; `src/preprocessing.py` re-checks
the split and writes `data/split_report.json`.

**Note on retrieval.** The pipeline in `src/pipeline.py` consumes the evidence span that ships
with each case (`retrieval.mode: oracle_evidence`), so the effect of the three agents can be
attributed without retrieval quality as a confounder, and the split stays leak-free. The
BM25 + Chroma hybrid retriever pictured in Figure 1 is a design component and is **not
queried** during the reported experiments; its parameters in the config are design values.
The paper states this explicitly under Figure 1.

## 7. Data preprocessing

```bash
python src/preprocessing.py          # verifies the frozen split, writes data/split_report.json
python src/preprocessing.py --rebuild # re-derives the 8:2 split in memory and re-checks leakage
```
Expected output ends with `ok: True`; the report shows `kb=400`, `test=100`,
`test_question_leak=0`, `test_evidence_leak=0`.

## 8. Training

There is **no training step and no checkpoint**. All three agents are few-shot prompts sent
to a hosted model; the prompts live in `src/pipeline.py` (`PROPOSER`, `REVISER`, `CHECKER`).
Reproducing the system therefore means re-running inference (§9), not fitting weights.

## 9. Inference / main experiment

```bash
# 100 test cases, 4 configurations (baseline, proposer, reviser, full) = 700 calls
python src/run_real_experiment.py --limit 5      # smoke test first
python src/run_real_experiment.py                # full run (~2.5 h)

# bare LLM baseline (no evidence), 100 cases, 3-level fallback on empty output
python src/run_bare_baseline.py --limit 5
python src/run_bare_baseline.py
```

`run_real_experiment.py` writes per-case predictions to `results/case_comparison_100.csv`,
token accounting to `results/token_ledger.csv`, latency/cost to `results/latency_cost.csv`,
and the ablation table to `results/table3_real.csv`. Progress is appended to
`results/real_run_progress.jsonl` (git-ignored, created on the first run), so an interrupted
run resumes where it stopped.

Evidence-poisoning experiment (Table 8), 27 cases × 2 conditions:

```bash
python src/run_injection.py
```

Deterministic version-filter baseline (Table 7), **zero model calls**, reads the committed
predictions:

```bash
python src/filter_baseline.py        # writes results/version_filter_eval.csv + summary json
```

## 10. Evaluation

```bash
python src/evaluate_metrics.py        # Table 1 / Table 3 + McNemar + Wilcoxon
python src/evaluate_hallucination.py  # Appendix C.5 rule, standalone
```

`src/evaluate_metrics.py` prints and writes `results/metrics_recomputed.csv`, plus
`results/table4_paired.csv` (McNemar on version hallucination, Wilcoxon on per-case F1).
Word F1, ROUGE-L, refusal and length live in `results/metrics_real.csv`; `results/table3_real.csv`
holds the strict-EM / Wilson-CI column of the ablation table, and `results/version_filter_summary.json`
holds the version-recall counts used in Table 2.
Metric definitions are documented in the docstring and in the paper (Appendix C.5, §4.3):
tokens are `re.findall(r"[a-z0-9]+", lower(text))`; word F1 uses token **sets**; ROUGE-L is
`2L/(m+n)` over the LCS of the same token stream; a version number absent from
`context ∪ gold` counts as one hallucinated case; refusal means the answer contains
`NOT COVERED`.

## 11. Expected results

`python src/evaluate_metrics.py` must print exactly (100 test cases):

| configuration | strict EM | word F1 | ROUGE-L | version halluc. | refusal | length |
|---|---|---|---|---|---|---|
| Bare LLM (zero-shot) | 0/100 | 0.1346 | 0.0619 | 0.69 | 0.00 | 501.0 |
| Single RAG (oracle ctx) | 0/100 | 0.2629 | 0.1492 | 0.35 | 0.00 | 121.1 |
| Proposer only | 0/100 | 0.2330 | 0.1371 | 0.11 | 0.12 | 99.2 |
| Proposer + Reviser | 0/100 | 0.2363 | 0.1429 | 0.03 | 0.15 | 77.5 |
| Full multi-agent | 0/100 | 0.2135 | 0.1354 | 0.00 | 0.16 | 49.4 |

Significance (exact McNemar on hallucination, Wilcoxon signed-rank on per-case F1):

| comparison | hallucination | McNemar | word F1 | Wilcoxon |
|---|---|---|---|---|
| bare → single RAG | 0.69 → 0.35 | b=37, c=3, p=1.9×10⁻⁸ | 0.1346 → 0.2629 | p=5.4×10⁻¹⁸ |
| single RAG → full | 0.35 → 0.00 | b=35, c=0, p=5.8×10⁻¹¹ | 0.2629 → 0.2135 | p=6.6×10⁻⁶ |
| bare → full | 0.69 → 0.00 | b=69, c=0, p=3.4×10⁻²¹ | 0.1346 → 0.2135 | p=1.5×10⁻⁹ |

Other committed results: `results/version_filter_summary.json` (the deterministic filter is a version-level
control only: version-level hallucination 0.00 and recall 14/15 vs 9/15, while component-version
pairing cannot be judged by a string rule and is therefore not scored; see Section 5.3), `results/injection_summary.csv` (propagation 0.93 → 0.52,
escape 0.11 → 0.37 for baseline vs. the full pipeline, with tamper and append injections), `results/fs_er_human_scores_20.csv`
(20-case human sheet: factual support 0.750 → 1.000, executable repair 0.950 → 0.350).

The two 20-case sheets are **hand-filled, not script-generated**: the coding rules are printed
in the `VC说明` column of `results/vc_scoring_template_20.csv`, and the author scored all 120
judgement dimensions (20 cases × 2 systems × VC/FS/ER) by reading each prediction.
`vc_scoring_template_20.csv` is the same sheet with the two VC columns left blank: it is a blank
form, not a second independent annotation. An AI-drafted suggestion was used as
a starting point and the author adopted it in every cell (agreement 100%), so the final sheet
and the suggestion coincide and only one file is shipped. Because this is a single annotator
with AI pre-annotation, the paper reports it as a consistency check and states the limited
power (FS b=0/c=5, p=0.0625; ER b=13/c=1, p=0.0018) rather than as a blind human study.

Strict EM is 0 for every configuration because gold answers are multi-step numbered
procedures; the paper reports this as a finding about the metric, not as a system failure.

Data-caveat notes: `token_ledger.csv` carries a `config` column because its 100 rows are the
sum of the four ablation configurations; `metrics_with_bare.csv` takes the latency and token
columns for single RAG and the full pipeline from `latency_cost.csv`; the 69 bare-model retries
are reported from the run log but were not logged per case, so `bare_preds.csv` has no retry
column; `cost_usd` is 0 everywhere because platform credit covered the calls.

## 16. Known limitations (stated in the paper)

* Evidence is oracle (dataset-annotated), so retrieval recall is out of scope.
* The 20-case FS/ER sheet is single-annotator; the AI pre-annotation was adopted 100%, so it
  is a consistency check, not an independent blind evaluation (FS p=0.0625, underpowered).
* The poisoning experiment covers 27 cases and one tampering family per case.
* Strict EM is degenerate on this dataset (multi-step gold answers); word F1 and ROUGE-L are
  the reported surface metrics.
